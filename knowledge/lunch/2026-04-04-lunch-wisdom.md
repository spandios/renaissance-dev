# 점심 지식 Deep Dive: 인간은 코드 안이 아니라 루프 위에 있어야 한다

**Source:** [Humans and Agents in Software Engineering Loops](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html)  
**Author:** Martin Fowler  
**Date:** 2026-04-04

---

## The Big Idea

**AI 시대의 소프트웨어 개발에서 인간의 최적 역할은 “코드를 직접 만드는 사람(in-the-loop)”도, “완전히 손 떼는 사람(out-of-the-loop)”도 아니라, 에이전트가 일하는 루프 자체를 설계·개선하는 사람(on-the-loop)이라는 주장이다.**

---

## Argument Breakdown

글의 논리는 단순한 “AI 찬반”이 아니라, 개발을 **루프 구조**로 재정의하는 데서 시작한다.

### 1) 개발에는 두 개의 루프가 있다: Why loop vs How loop

- **Why loop**: 아이디어를 제품 결과로 바꾸는 루프(무엇을/왜 만드는가)
- **How loop**: 실제 구현 루프(코드·테스트·인프라·설계 문서·ADR 등)

핵심은 산출물(코드, 문서)이 목적이 아니라 **결과를 위한 중간 매개체**라는 점이다.

### 2) 극단 1 — 인간이 How loop에서 완전히 빠지는 모델의 매력과 한계

“바이브 코딩”처럼 인간은 요구사항만 말하고 에이전트가 구현을 반복하게 하는 방식은 속도감이 크다. 실제로 초안 생성은 매우 빠르다.

하지만 Fowler는 여기서 중요한 반론을 던진다.

- 내부 품질(구조, 가독성, 응집도)은 여전히 외부 품질(속도/비용/안정성)에 영향
- 코드가 스파게티가 되면 에이전트도 이해/수정 비용이 커져 **spiral**이 늘어남
- 결국 “사람이 보기 좋은 코드” 문제가 아니라, **시스템이 지속적으로 바뀔 수 있는 코드** 문제

즉, 내부 품질의 중요성은 AI 시대에도 사라지지 않는다. 이유만 바뀐다.

### 3) 극단 2 — 인간이 최하위 루프에서 매 줄 리뷰하는 모델의 병목

반대로 인간이 계속 코드 생성 결과를 직접 검토하면 품질은 통제되지만 속도가 죽는다.

- 에이전트 생성 속도 > 인간 검토 속도
- 리뷰 병목으로 인해 AI 생산성 이득 상쇄
- “사람이 다 본다”는 안전장치는 확장성이 낮음

여기서 글은 테스트 자동화의 역사와 같은 **shift-left**를 제시한다. QA를 뒤로 미루지 않듯, 에이전트 품질 검증도 인간 수동 리뷰 뒤에 두지 말고 앞당겨야 한다.

### 4) 해법 — Humans on the loop (Harness Engineering)

글의 핵심 제안은 **하네스(harness) 엔지니어링**이다.

하네스란 에이전트가 일하는 작업 환경 전체를 뜻한다.
- 스펙/제약
- 품질 기준(테스트, eval, 린트, 보안 규칙)
- 실행 워크플로우와 단계별 검증

문제가 생겼을 때 행동 차이가 중요하다.
- in-the-loop: 결과물을 직접 고친다
- on-the-loop: **그 결과를 만든 하네스를 고친다**

즉, “한 번의 수정”이 아니라 “다음부터 계속 좋아지는 구조”를 만든다.

### 5) 다음 단계 — Agentic flywheel

더 나아가 에이전트가 하네스 개선 제안까지 하게 만들 수 있다.

- 테스트/운영지표/사용자 행동/비용 데이터를 입력으로 제공
- 에이전트가 개선안을 추천
- 인간은 리스크·효익 기준으로 승인 정책 설계
- 점진적으로 일부 저위험 개선은 자동 승인

이때의 목표는 단발성 자동화가 아니라, **자기개선하는 개발 시스템**이다.

## Context: 왜 지금 중요한가

2026년의 개발팀은 공통적으로 같은 문제를 겪고 있다.

1. 에이전트 도입은 빨라졌는데, 운영 규율은 뒤처짐  
2. 개인 역량 편차보다 “팀의 AI 운영 시스템” 편차가 성과를 가름  
3. 코드 생성보다 변경 관리/품질 보증/비용 통제가 더 큰 경쟁력 요소가 됨

이 글은 그 전환점을 정확히 짚는다. 앞으로의 차별화는 “누가 더 빨리 코드를 뽑느냐”보다, **누가 더 빨리 학습하는 루프를 설계하느냐**다.

## Application: 개발자로서 어떻게 적용할 것인가

### 1) 리뷰 중심에서 하네스 중심으로 업무를 재배치

- PR에서 코드 라인 단위 지적 비중을 줄이고
- 테스트 기준, 실패 기준, 품질 게이트를 먼저 정의
- “이 코드가 맞나?”보다 “이 루프가 계속 맞는 코드를 만들 수 있나?”를 질문

### 2) beauty-sale에 바로 적용할 3가지

1. **크롤러/가격집계 파이프라인 하네스화**  
   - 수집 성공률, 가격 이상치, 지연시간, 재시도 비용을 자동 측정
2. **PR 품질 게이트 강화**  
   - 회귀 테스트 + 성능 임계치 + SQL anti-pattern 검사 자동화
3. **에이전트 수정 제안 루프 도입**  
   - 실패 로그 기반으로 “테스트/프롬프트/규칙” 개선안 생성 → 주간 승인

### 3) 팀 커뮤니케이션 문법 전환

- “AI가 잘/못했다” 대신
- “하네스의 어떤 규칙이 이 결과를 만들었는가”로 회고 프레임 전환

사람 탓/모델 탓보다 시스템 개선 속도가 빨라진다.

### 4) 면접/이직 관점에서의 포지셔닝

7년차 이상에선 단순 코딩 숙련보다 **개발 시스템 설계 역량**을 본다.

이 글의 관점으로 답하면 강하다.
- “AI 도구를 쓸 줄 안다”를 넘어서
- “AI가 일관되게 좋은 결과를 내는 루프를 설계해봤다”로 차별화 가능

---

## 한 줄 정리

**AI 시대의 시니어 개발자는 코드 생산자가 아니라, 코드 생산 시스템의 설계자다.**
