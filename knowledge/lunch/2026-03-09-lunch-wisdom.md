## 🎯 The Big Idea

> **"AI 분석의 출력은 항상 자신감 있어 보인다. 하지만 거짓말로 가득할 수 있다: 조작된 인용문, 거짓 인사이트, 완전히 잘못된 결론."**

AI로 고객 데이터를 분석할 때, 결과는 항상 설득력 있어 보입니다. 하지만 **보이지 않는 오류**들이 숨어 있습니다. 3개월 후 결정이 무너지거나, "고객 증거"가 사실은 엄청난 허점을 가지고 있다는 걸 깨닫게 됩니다.

Caitlin Sullivan은 2,000+ 시간의 AI 분석 워크플로우 테스트를 통해 **4가지 핵심 실패 모드**와 이를 방지하는 검증된 프롬프트 기법을 발견했습니다. 이 기법들은 Claude, ChatGPT, Gemini 모두에서 작동하며, 인터뷰, 설문조사, 모든 정성적/혼합 데이터에 적용됩니다.

## 📖 Argument Breakdown

### 1. 왜 AI는 고객 데이터 분석에 실패하는가?

**인터뷰는 비구조적이고 지저분하다**
- 45분 인터뷰 = 엉망진창의 대화
- 참가자는 자기 모순적, 탄젠트로 벗어남, 8분에 말한 것을 35분에 완전히 재구성
- **LLM의 대응**: 구조를 부과하고 결론으로 너무 빨리 점프
  - 깔끔한 테마를 즉시 찾음
  - 가장 잘 맞는 인용문 선택
  - 깔끔한 요약 생성
  - 끝!

**하지만 진짜 분석은 다르다**
- 엉망진창 속에 앉아 있기
- 모순 발견
- 탄젠트 무게 측정
- 톤 변화 포착

→ **명시적 가이드 없이는, AI는 이 모든 것을 "인사이트처럼 보이지만 실제로는 중요한 것을 놓친" 것으로 평평하게 만든다.**

**설문조사는 구조적으로 보이지만, 그렇지 않다**
- CSV = 쉬워 보임. 하지만 아니다.
- "왜 취소했나요?" 200개 응답 = 인터뷰 데이터만큼 지저분 (맥락 없음)
- **CSV는 생각보다 깨끗하지 않다**:
  - 도구마다 다르게 내보내기 (SurveyMonkey vs Qualtrics)
  - 메타데이터 컬럼 (타임스탬프, 내부 태그) = 고객 응답 옆에 앉아있음
  - AI에게 어떤 컬럼이 고객 목소리인지 알려주지 않으면 → 모든 것을 신호로 분석
  - 예: 내부 노트 ("follow-up으로 플래그") → AI가 고객이 말한 것으로 취급

→ **AI 모델은 인터뷰에서는 구조, 증거 추출, 모순 탐지에 도움이 필요. 설문조사에서는 해석, 컬럼 구분, 희소 응답의 실제 의미 이해에 도움이 필요.**

### 2. 모델별 차이: Claude vs ChatGPT vs Gemini

Caitlin은 같은 분석을 100번 이상 실행해서 모델별 차이를 발견했습니다.

**Claude: 깊이와 뉘앙스 최고**
- 더 많은 인용문, 더 많은 영역 커버
- 트레이드오프: 전체 브레인 덤프 → 테마가 항상 "증명된" 것은 아님
- 넓이를 원하지만, 안전한 패턴만은 아님

**Gemini (+ NotebookLM): 강하게 검증된 테마**
- 더 적은 테마, 하지만 더 강한 근거
- 여러 번 프롬프트해야 완전성 확보
- 더 긴 인용문 요청 필요
- **독특한 장점**: 비디오에서 비언어적 행동 분석 가능 (다른 모델은 아직 불가)

**ChatGPT: 최종 프레이밍 & 이해관계자 커뮤니케이션**
- 세 모델 중 가장 창의적 (불행히도 "실제 인용문"에서도 창의적)
- **실제 증거에 대한 신뢰도 최하**: 인용문 결합
- 특정 청중을 위한 관련 발견 사항 패키징에 탁월

**Caitlin의 추천**: **분석 작업에는 Claude 사용**
- 실제 데이터에 뿌리를 두고 더 많은 영역을 커버
- 깊이와 넓이를 밀어붙이지 않고 얻음
- 트레이드오프: 필터링 안 해줌 → 검증된 패턴과 반쯤 형성된 가설이 동등하게 제시됨 → 테마가 잘 증거되었는지 검증 필요
- 하지만 이게 더 나은 출발점 (무언가 놓쳤는지 확신하기 위해 3번 프롬프트하는 것보다)

### 3. 실패 모드 #1: Invented Evidence (허구 증거)

**할루시네이션은 여전히 풍부하다**

2가지 유형:
1. **완전히 허구의 인용문** (모든 주요 LLM에서 여전히 발생)
2. **프랑켄슈타인 인용문**: 여러 소스에서 꿰맨 것 (ChatGPT에서 특히 흔함)

**왜 발생하나?**
- 프롬프트 방식 때문
- "max 100 words" 또는 "각 테마에 대해 12단어 이하의 짧고 대표적인 인용문" → 거의 항상 mash-up

**근본 원인**
- LLM은 검색 엔진처럼 인용문을 검색하지 않음
- **텍스트를 생성**: 맥락을 고려해 통계적으로 가능성 있는 텍스트
- 생성 ≠ 검색
- 맥락이 "전화 확인 좌절"이면 → 전화 확인 좌절 언어 생성
- 때로는 원본과 일치, 때로는 거의 일치, 때로는 허구

**"Verbatim"도 애매하다**
- 정확한 문자? 구두점은 다를 수 있나? 필러 단어는? 인용문은 어디서 시작하고 끝나나?
- 모델은 이 간격을 당신이 볼 수 없는 가정으로 채움
- 참가자 ID와 타임스탬프도 가짜일 수 있음: `[P03, 14:30]` = 권위적으로 보이지만 인용문이 허구면 의미 없음

---

**해결책: 2단계**

**1단계: 인용문 "규칙" 정의**

프롬프트에 추가:
```
QUOTE SELECTION RULES
- 생각이 시작되는 곳에서 시작하여, 완전히 표현될 때까지 계속
- 결론뿐 아니라 추론도 포함
- 헤지와 한정사 유지 — 불확실성 신호
- 존재할 때 감정적 언어 포함
- 참가자 ID와 대략적인 타임스탬프로 인용 [P02 ~14:30]
- 인터뷰의 다른 부분에서 온 진술을 결합하지 마라
- 인용문이 3문장을 초과하면, 별도의 인용문으로 분할
```

→ **애매함 제거. 모델은 이제 "verbatim"이 당신에게 무엇을 의미하는지 안다: 어디서 시작, 어디서 멈춤, 무엇을 포함, 무엇을 결합하지 말아야.**

**2단계: 사용 전 검증**

초기 분석 후, 이 검증 프롬프트 사용:
```
QUOTE VERIFICATION
위 분석의 각 인용문에 대해:
- 인용문이 소스 transcript에 verbatim으로 존재하는지 확인
- 인용문이 가까운 paraphrase이지만 정확하지 않으면, 플래그하고 실제 wording 제공
- 인용문을 찾을 수 없으면, NOT FOUND로 표시

출력 형식:
- Quote: [the quote]
- Status: VERIFIED / PARAPHRASE / NOT FOUND
- If paraphrase: Actual wording: [what they said]
- Location: [Participant ID, timestamp, or line number]
```

**결과**: 대부분의 인용문이 paraphrase되었음을 발견 (원본 verbatim 고객 진술이 아님)

→ **검증 없이는, 이런 "인용문"이 덱에 들어가 실제 참가자에게 귀속됨. 때로는 큰 문제 없음. 때로는 강하게 공감하는 제품 언어 vs 전환되지 않는 메시징의 차이.**

### 4. 실패 모드 #2: False or Generic Insights (거짓/일반적 인사이트)

**AI는 너무 넓고 일반적이어서 행동할 수 없는 테마를 찾는다**

PM들이 계속 말하는 것:
- "AI 분석이 내가 이미 아는 것만 말해줬어"
- "이 인사이트는 너무 일반적. 나는 아무것도 할 수 없어."

**출력 예시**:
- "가격은 결정의 요인"
- "사람들은 신뢰성을 중요하게 생각"
- "사용자는 더 많은 실시간 정보를 원함"

→ **사실일 수 있지만, 어려운 결정에 쓸모없음**

이 테마들은 그 카테고리의 어떤 제품도 설명할 수 있습니다. 사용자가 이 새 기능을 투자를 정당화할 만큼 충분히 원하는지, 또는 추가하면 당신을 선택한 고객들을 소외시킬지 알려주지 않습니다.

**왜 발생하나?**

1. **AI는 합의를 찾는 것이 기본값** (LLM = 패턴 찾기 기계)
   - 여러 참가자가 언급한 것 찾기
   - 패턴 매칭된 테마 생성
   - 쉽게 떠오르는 (명백한) 패턴 표면화

2. **가장 중요한 인사이트는 숨어있을 수 있다**
   - 이 특정 인터뷰 배치에서 몇 명만 말한 것
   - 하지만 더 많은 고객들과 공유되면 주목할 만한 비즈니스 신호
   - 또는 사람들이 원한다고 말하는 것 vs 행동이 제안하는 것 사이의 긴장

3. **LLM은 훈련에서 prior를 가져온다**
   - 수천 개의 churn 분석에서 가격이 #1 테마였다면
   - 전체 데이터셋이 지원하지 않더라도 가격 쪽으로 가중치

**설문조사에서는 더 나쁘다**

"It's not for me" (취소 이유) → AI는 추측해야 함

맥락 없이 → "value perception" 테마로 덩어리로 묶임

하지만 "not worth it"은 의미할 수 있다:
- 얻는 것에 비해 너무 비쌈
- 너무 데이터 집약적이고 나는 충분히 진지한 운동선수가 아님
- 충전할 또 다른 장치를 원하지 않음
- 화면이 필요한데 Whoop에는 없음

→ **하나의 응답, 네 가지 완전히 다른 제품 결정 의미**

수백 개의 설문조사 응답에 걸쳐 이 애매함을 곱하면 → 테마는 의미 없는 평균이 되어 결정을 더 쉽게 만들지 못함.

**해결책: 효과적인 컨텍스트 로딩**

대부분의 사람들은 Role, Context, Task, Format 같은 프롬프트 프레임워크에 익숙합니다. Context는 대부분 프롬프트 시작 부근에 몇 줄의 배경 정보를 포함하는 것을 의미합니다.

AI를 분석에 사용할 때, 이는 종종 현재 고객 발견의 요점에 초점을 맞춥니다: 목표, 가설, 우리가 작업 중인 제품의 어떤 부분.

**하지만 3줄 목표도, 전체 비구조적 뒷이야기도 충분하지 않다.**

**효과적인 컨텍스트 로딩은 최소 4가지 구성요소를 가진다:**

**1. Project Context (프로젝트 맥락)**
- AI에게 범위와 이해관계 알려줌
- "화면을 추가할지 탐색" = 제약이 있는 특정 결정
- "고객 연구 수행" = 모호 → AI는 프레임을 주지 않았기 때문에 일반적 분석으로 기본값

**2. Business Goal (비즈니스 목표)**
- AI에게 당신이 달성하려는 것 알려줌
- 기능이 새 사용자를 유치할지 vs 기존 사용자를 소외시킬지 알아야 우선순위를 정할 수 있다면 → 말해라
- AI는 당신의 질문에 답하고 당신의 결정을 다루는 쪽으로 증거를 가중치 부여 (AI가 가정하는 결정이 아니라)

**3. Product Context (제품 맥락)**
- AI에게 도메인 지식 제공
- 이것 없이, AI는 "내 데이터를 보고 싶어"를 일반적으로 해석
- 이것과 함께, AI는 그 진술을 Apple Watch와 경쟁하는 screenless wearable의 맥락에서 이해 — 완전히 다른 해석

**4. Participant Overview (참가자 개요)**
- AI에게 누가 말하는지 알려줌
- 이탈한 Garmin switcher의 "실시간 데이터 필요" ≠ 경쟁사를 시도해본 적 없는 충성 사용자의 같은 말
- AI는 증거가 어디서 오는지 알 때만 증거를 올바르게 가중치 부여 가능

**좋은 소식**: 사람들이 프롬프트의 컨텍스트에 추가하는 것의 많은 부분은 불필요합니다. 생각하는 것만큼 많은 정보가 필요하지 않지만, 명확하고 직접적이며 관련성 있는 정보가 필요합니다 (위 4가지처럼).

---

### 5. 실패 모드 #3: Signal That Doesn't Guide Decisions (결정을 돕지 못하는 신호)

이 부분은 글이 잘려서 전체 내용을 확인할 수 없지만, 핵심은:
- AI가 찾는 "신호"가 실제로 제품 결정을 내리는 데 도움이 되지 않음
- 너무 일반적이거나, 실행 가능하지 않거나, 모순됨

---

### 6. 실패 모드 #4: Contradictory Insights (모순된 인사이트)

역시 글이 잘려서 전체 내용을 확인할 수 없지만, 핵심은:
- AI가 서로 모순되는 인사이트를 생성
- 이를 감지하고 해결하는 메커니즘 필요

---

## 🌍 Context: 이 글이 왜 지금 중요한가?

### 1. AI 분석이 일상화되고 있다
- 모든 PM, 개발자, 리서처가 ChatGPT/Claude로 데이터 분석
- 하지만 대부분 검증 없이 결과 신뢰
- 잘못된 결정으로 이어짐 ($수백만 규모)

### 2. "AI가 말한 것" = 신뢰할 수 있는 것처럼 보인다
- 출력이 항상 자신감 있어 보임
- 오류는 보이지 않음 (이해관계자가 질문하거나, 3개월 후 결정이 무너지거나, "고객 증거"에 큰 허점이 있다는 걸 깨닫기 전까지)
- **보이지 않는 오류가 가장 위험**

### 3. 모델별 차이를 이해하는 사람이 적다
- ChatGPT = 가장 널리 사용됨, 하지만 인용문 신뢰도 최하
- Claude = 분석에 최적, 하지만 필터링 안 함
- Gemini = 강하게 검증됨, 하지만 여러 번 프롬프트 필요

### 4. beauty-sale 같은 프로젝트에 직접 적용 가능
- GA4 데이터 분석
- 사용자 피드백 분석
- 가격 비교 패턴 발견
- 리뷰 감정 분석

## 💼 Application: 개발자로서 어떻게 적용할 것인가?

### 1. beauty-sale GA4 분석에 즉시 적용

**현재 문제**
- GA4에서 사용자 행동 데이터 쌓이고 있음
- ChatGPT에게 "이 데이터 분석해줘" → 일반적 인사이트만 받음
- "사용자들은 가격을 중요하게 생각합니다" → 쓸모없음

**Caitlin의 4가지 컨텍스트 적용**

```
PROJECT CONTEXT
beauty-sale는 K-뷰티 멀티 플랫폼 가격 비교 앱입니다.
현재 "리뷰 통합" 기능을 추가할지 결정 중입니다.
GA4 데이터로 사용자들이 가격 비교 후 무엇을 하는지 파악하려 합니다.

BUSINESS GOAL
리뷰 통합 기능이 사용자 전환율을 높일지, 아니면 기존 "빠른 가격 비교" 
가치 제안을 희석시킬지 결정해야 합니다.
만약 리뷰를 보는 사용자가 구매 전환이 높다면 → 투자 정당화
만약 가격만 보는 사용자가 전환이 높다면 → 리뷰는 우선순위 낮음

PRODUCT CONTEXT
beauty-sale는 "가장 빠른 가격 찾기"를 차별점으로 합니다.
경쟁사: 화해 (리뷰 중심), 글로우픽 (큐레이션), 올리브영 (단일 플랫폼)
현재 우리는 속도와 단순함으로 경쟁합니다.

PARTICIPANT OVERVIEW
GA4 데이터는 지난 30일 1,000명 사용자입니다.
- 70%: 모바일 (빠른 구매 결정)
- 30%: 데스크톱 (리서치 모드)
- 세그먼트: 신규 vs 재방문, 구매 전환 vs 이탈
```

**결과 예상**
- "사용자들은 가격을 중요하게 생각합니다" ❌
- "모바일 사용자 중 재방문자는 평균 3개 플랫폼만 확인하고 즉시 구매. 리뷰를 보려고 외부 사이트로 이탈하는 비율 12%. 이 12%가 리뷰 통합 타겟. 하지만 신규 사용자는 평균 7개 플랫폼 확인하며 가격만 비교. 리뷰 추가 시 이 그룹의 '빠른 가격 찾기' 인식 희석 가능." ✅

### 2. 사용자 피드백 분석 (설문조사/인터뷰)

**앱 스토어 리뷰 분석**

현재 방식:
```
"이 100개 리뷰를 분석해서 테마 찾아줘"
→ "사용자들은 UI 개선을 원합니다" (쓸모없음)
```

**Caitlin 방식**:

**1단계: 인용문 규칙 정의**
```
QUOTE SELECTION RULES FOR APP REVIEWS
- 전체 리뷰 텍스트에서 특정 기능/문제를 언급한 부분만 추출
- 감정 표현 포함 ("짜증", "최고", "실망")
- 별점과 함께 인용 [★★★★★ - 사용자123]
- 여러 리뷰의 문장을 결합하지 마라
- 15단어 이하로 제한하지 마라 (맥락 필요)
```

**2단계: 검증 프롬프트**
```
QUOTE VERIFICATION
위에서 추출한 각 인용문이 실제 리뷰에 존재하는지 확인.
- Status: VERIFIED / PARAPHRASE / NOT FOUND
- If paraphrase: 실제 리뷰 텍스트 제공
```

**3단계: 4가지 컨텍스트**
```
PROJECT CONTEXT: beauty-sale 리뷰 통합 기능 결정
BUSINESS GOAL: 리뷰 추가 시 사용자 만족도 vs 복잡도 증가 트레이드오프
PRODUCT CONTEXT: 빠른 가격 비교가 차별점
PARTICIPANT OVERVIEW: 앱 스토어 리뷰 100개 (최근 30일, 별점 3-5점)
```

**결과 예상**
- 일반적: "UI 개선 필요" ❌
- 구체적: "★★★★☆ - '가격은 빠른데 리뷰가 없어서 다른 앱으로 갔어요' (7명) vs ★★★★★ - '다른 앱보다 빠르고 간단해서 좋아요. 리뷰 추가하면 복잡해질까봐 걱정' (12명)" ✅

→ **리뷰 추가 = 7명 만족, 12명 불만족 가능성 → 신중한 접근 필요**

### 3. 이직 면접에서 활용: "AI로 데이터 분석" 사례

**질문: "데이터 기반 의사결정 경험이 있나요?"**

**나쁜 답변**
> "ChatGPT로 GA4 데이터 분석했습니다."

**좋은 답변** (Caitlin 기반)
> "beauty-sale에서 리뷰 통합 기능을 추가할지 결정하기 위해 GA4 데이터를 분석했습니다. 처음에는 ChatGPT에게 '사용자 행동 분석해줘'라고 했더니 '사용자들은 가격을 중요하게 생각합니다' 같은 일반적 인사이트만 나왔습니다.
> 
> 그래서 **4가지 컨텍스트 로딩** 기법을 적용했습니다:
> 1. 프로젝트 맥락: 리뷰 통합 기능 결정
> 2. 비즈니스 목표: 전환율 vs 단순함 트레이드오프
> 3. 제품 맥락: 빠른 가격 비교가 차별점
> 4. 참가자 개요: 모바일 70%, 신규 vs 재방문 세그먼트
> 
> 결과, **재방문 모바일 사용자 12%가 리뷰 때문에 외부 사이트로 이탈**한다는 것을 발견했습니다. 하지만 **신규 사용자는 가격만 비교**하므로, 리뷰 추가 시 '빠른 가격 찾기' 인식이 희석될 위험이 있었습니다.
> 
> 최종 결정: 리뷰 통합을 추가하되, **재방문자에게만 노출하는 A/B 테스트** 진행. 결과, 재방문자 전환율 15% 증가, 신규 사용자 영향 없음."

→ **데이터 → 맥락화 → 검증 → 세그먼트별 인사이트 → 실행 가능한 결정**

## 📌 Key Takeaways

1. **AI 분석의 4가지 실패 모드**
   - Invented evidence (허구 증거)
   - False/generic insights (일반적 인사이트)
   - Signal that doesn't guide decisions (결정을 돕지 못하는 신호)
   - Contradictory insights (모순된 인사이트)

2. **모델별 강점 활용**
   - Claude: 깊이와 뉘앙스 (분석)
   - Gemini: 강하게 검증된 테마 (검증)
   - ChatGPT: 최종 프레이밍 (커뮤니케이션)

3. **인용문 검증은 필수**
   - "QUOTE SELECTION RULES" 정의
   - "QUOTE VERIFICATION" 프롬프트
   - 대부분의 인용문은 paraphrase → 원본 확인 필수

4. **4가지 컨텍스트 로딩**
   - Project Context (프로젝트 맥락)
   - Business Goal (비즈니스 목표)
   - Product Context (제품 맥락)
   - Participant Overview (참가자 개요)

5. **beauty-sale 즉시 적용**
   - GA4 데이터 분석
   - 앱 스토어 리뷰 분석
   - 리뷰 통합 기능 결정

6. **이직 면접 무기**
   - "AI로 데이터 분석" 사례
   - STAR 답변 준비
   - 검증된 프로세스 강조
