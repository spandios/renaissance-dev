## 1. The Big Idea (핵심 관통하기)

**AI가 코드의 80%를 써주는 시대에, 개발자의 진짜 위기는 "코드를 못 쓰는 것"이 아니라 "자기 코드를 이해하지 못하는 것"이다.**

Andrej Karpathy의 "몇 주 만에 80% 수동 코딩에서 80% 에이전트 코딩으로 뒤집혔다"는 발언이 촉발점. Claude Code 팀은 하루 20+ PR을 전부 AI로 작성. 숫자 자체보다 중요한 건, 문제의 **본질**이 바뀌었다는 것.

---

## 2. Argument Breakdown (논리 해부)

### 단계 1: 에러의 본질이 바뀌었다

과거 AI 에러는 문법 오류나 단순 버그였다. 지금은 **개념적·아키텍처적 실패**로 진화했다.

- **가정 전파(assumption propagation):** 모델이 초반에 잘못 이해한 가정 위에 전체 기능을 쌓아올림. 5개의 PR이 쌓인 후에야 아키텍처가 틀렸다는 걸 깨달음.
- **추상화 과잉:** 100줄이면 충분한 걸 1,000줄짜리 클래스 계층으로 만듦. "포괄적으로 보이는 것"을 최적화하는 문제.
- 시스템 프롬프트나 계획 모드로도 해결 불가 — 에이전트는 "일관된 출력"에 최적화되었지, "당신의 전제를 의심"하도록 만들어지지 않았기 때문.

### 단계 2: 이해 부채(Comprehension Debt)의 등장

Jeremy Twei가 명명한 개념. 핵심 메커니즘:

1. AI가 그럴듯한 코드를 생성 → 테스트 통과
2. 출시 압박 + 에이전트의 자신감 → "대충 훑어보고 머지"
3. 며칠 후 그 코드가 어떻게 동작하는지 설명 불가
4. **코드 생성 능력(generation) ≠ 코드 이해 능력(discrimination)**
5. 리뷰가 "도장 찍기"로 전락 → 자기 코드베이스를 점점 이해하지 못하게 됨

Osmani 본인의 고백: "Claude가 기능을 구현했고, 테스트 통과해서 머지했다. 3일 후 그게 어떻게 작동하는지 설명할 수 없었다."

### 단계 3: 생산성 역설

데이터가 모순을 드러낸다:

| 지표 | 변화 |
|------|------|
| 머지 PR 수 | +98% |
| PR 크기 | +154% |
| 리뷰 시간 | +91% |
| 주당 절약 시간 (자가 보고) | 10시간+ |
| 전체 업무량 감소 | ❌ 없음 |

절약한 시간은 컨텍스트 전환, 조율 오버헤드, 늘어난 변경사항 관리로 소진됨. **"더 빠른 차를 샀는데 도로가 더 막힌다"** — 제본스 역설의 정확한 구현.

### 단계 4: 개발자 정체성의 분기

Karpathy의 핵심 관찰:

- **"코딩을 좋아하는 사람"** → 상실감. 장인정신과 명상 같은 느낌의 소멸.
- **"만드는 것을 좋아하는 사람"** → 해방감. 코드는 수단일 뿐.
- 도구는 후자를 위해 최적화되고 있음.

Armin Ronacher 5,000명 설문 결과: 44%는 여전히 90%+ 수동 코딩 vs 극소수는 100% AI. **정규분포가 아닌 양극화 분포.**

성공 패턴: **구현자(implementer) → 조율자(orchestrator)** 로의 역할 재정의. 명령형 → 선언적 사고로의 전환.

## 3. Why It Matters (왜 중요한가)

### 시장 상황
- AI 코딩 도구가 성숙기 진입 (Claude Code, Cursor, Copilot 등)
- 기업들이 "AI로 몇 배 생산성 향상" 내러티브에 투자 중
- 하지만 실제 데이터는 **코드 리뷰가 새로운 병목**임을 보여줌

### 기술 트렌드
- "Vibe Coding" 유행 속에서 경고등이 켜지고 있음
- 코드 생성은 쉬워졌지만 **코드 이해와 유지보수**의 비용이 급증
- 제본스 역설: 코드 생성이 싸지면 → 코드 총량 증가 → 이해 비용 폭증

### 산업적 함의
- **그린필드/MVP**: AI 에이전트 80%가 현실적이고 효과적
- **성숙한 코드베이스**: 에이전트는 "모르는 걸 모름" + "과도한 자신감" → 위험
- 조직 차원에서 코드 리뷰 프로세스 재설계가 필요한 시점

## 4. 💼 For Engineers (개발자에게)

### 즉시 적용할 수 있는 행동 지침

1. **"머지 전 설명 테스트" 도입**: AI가 생성한 코드를 머지하기 전에, 자신이 동료에게 설명할 수 있는지 자문. 설명 못하면 머지하지 않기.

2. **이해 부채 감사(audit) 습관**: 주 1회, AI가 작성한 코드 중 가장 큰 PR을 골라 처음부터 읽으며 "이해 점수" 매기기. 3점 이하면 리팩토링.

3. **PR 크기 제한 유지**: AI가 대량 코드를 쏟아내도, 리뷰 가능한 단위(300줄 이하)로 분할. "리뷰 = 도장 찍기" 함정 방지.

4. **역할 재정의 수용**: 코딩 장인정신에 집착하기보다, **아키텍처 감독자 + 품질 관리자**로 역할 전환. 에이전트를 주니어 개발자로 보고 "코드 리뷰어"로서의 역량 강화.

5. **선언적 사고 훈련**: AI에게 "어떻게(how)" 대신 "무엇을(what)" 지시하는 연습. 시스템 설계, 제약 조건, 불변성 정의에 시간 투자.

### beauty-sale 프로젝트 적용

K-뷰티 가격 비교 앱처럼 여러 플랫폼 크롤링 + 가격 비교 로직이 있는 프로젝트에서:
- AI가 크롤러를 빠르게 생성하더라도, **각 플랫폼의 가격 정책/할인 규칙에 대한 이해**를 잃으면 안 됨
- "이 크롤러가 왜 이 셀렉터를 쓰는지" 설명할 수 없다면 이해 부채 발생 중
