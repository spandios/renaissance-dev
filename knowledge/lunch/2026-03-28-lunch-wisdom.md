# 점심 지식 Deep Dive: Agents Over Bubbles — "거품 논쟁"보다 중요한 것

**Source:** [Stratechery — Agents Over Bubbles](https://stratechery.com/2026/agents-over-bubbles/)  
**Date:** 2026-03-28  
**Author:** Ben Thompson

---

## The Big Idea

**지금 AI 시장의 핵심은 "거품인지 아닌지"가 아니라, 에이전트가 실제 업무에서 인간의 조정 비용을 줄여 생산성을 구조적으로 끌어올리는 단계에 들어섰다는 점이다.**

---

## Argument Breakdown

### 1) LLM의 진화는 "정답률"이 아니라 "작업 완결성"으로 이동했다

글은 AI의 전환점을 3단계로 본다.

1. **ChatGPT 단계**: 누구나 LLM의 잠재력을 체감했지만, 환각과 불안정성이 컸다.  
2. **Reasoning 모델 단계(o1 등)**: 답변 전 자기검증이 들어가며 신뢰도가 상승했다.  
3. **Agent 단계(Opus/Codex + harness)**: 모델이 답변만 내는 게 아니라, 도구를 호출하고 결과를 검증하며 "일을 끝내는 흐름"이 생겼다.

핵심은 3단계에서 모델 자체보다 **harness(에이전트 제어 레이어)**가 중요해졌다는 점이다. 즉, 성능은 "좋은 답변"에서 "완료 가능한 실행"으로 평가 축이 바뀌었다.

### 2) 에이전트는 인간의 가장 비싼 비용인 "조정 비용"을 줄인다

대기업은 소수의 핵심 인재가 방향을 잡고, 다수의 조직이 실행을 확장한다. 문제는 이 구조가 커질수록 커뮤니케이션, 승인, 재작업 비용이 급증한다는 것.

에이전트는 이 조정 비용을 직접 깎는다.

- 반복 업무를 병렬 실행
- 결과를 자동 검증
- 실패 시 재시도 루프 자동화
- 사람은 목표/품질 기준만 설정

따라서 AI의 경제 효과는 단순 인건비 절감이 아니라, **조직 마찰 감소 + 실행 속도 증가**로 나타난다.

### 3) 왜 하이퍼스케일러의 CapEx가 계속 커지는가

글은 "수요가 실제라서"라고 본다.

- Reasoning은 토큰 사용량을 크게 늘린다.
- 에이전트는 한 작업에 여러 번 모델 호출한다.
- 에이전트 오케스트레이션/검증에는 CPU 중심 워크로드도 추가된다.
- 그리고 유용성이 커지면 사용량 자체가 기하급수적으로 늘어난다.

즉, 인프라 투자는 선행투기가 아니라 **이미 발생한 병목 해소 투자**라는 해석이다.

### 4) 대중 전체가 AI를 잘 써야만 폭발하는 게 아니다

중요한 포인트는 "에이전시(주도적 활용 능력)의 필요 인구가 줄어든다"는 주장이다.

- 이전: 많은 사용자가 직접 프롬프트/검증을 잘해야 가치가 나옴
- 지금: 소수의 고숙련 사용자가 다수의 에이전트를 관리해 큰 산출을 냄

이건 생산성의 확산 경로를 바꾼다. 폭넓은 대중 채택 이전에도, 특정 조직/팀에서 경제적 충격이 먼저 나타날 수 있다.

### 5) 모델은 commodity가 되고 끝날까? 에이전트는 다르게 본다

글은 "모델만 보면 commoditization이 맞아 보이지만, 에이전트는 모델+하네스 통합이 성능을 좌우한다"고 말한다.

즉 이익은 모듈화된 파츠보다 **통합된 실행 경험**으로 이동한다.

- 단일 모델 점수보다
- 업무 맥락 연결, 도구 호출 안정성, 권한/보안, 재시도 품질, 결과 검증 체계가 경쟁력

이 관점은 "누가 모델을 만들었나"보다 "누가 일을 끝내는 시스템을 제공하나"를 더 중요하게 만든다.

---

## Context: 왜 지금 중요한가

2026년 현재 개발조직은 두 압력을 동시에 받는다.

1. **비용 압력**: 인건비와 인프라비 모두 증가
2. **속도 압력**: 제품 출시 주기는 더 짧아짐

여기서 에이전트는 단순 자동화 도구가 아니라, "소수 정예 팀이 대규모 실행력을 확보하는 방식"이 된다.

특히 1인/소규모 팀이 많은 스타트업·사이드프로젝트 환경에서, 에이전트는 인력 대체라기보다 **실행 레버리지**다. 같은 인원이 더 많은 실험을 짧은 주기로 돌릴 수 있기 때문이다.

## Application: 개발자로서의 적용법

### 1) "답변 생성"보다 "완료형 워크플로우"를 설계하라

- 코드 생성 → 테스트 실행 → 실패원인 분석 → 수정 → 재검증
- 문서 초안 → 사실검증 → 링크체크 → 요약본 배포

에이전트를 쓸 때는 항상 "끝까지 닫히는 루프"를 먼저 설계한다.

### 2) 검증 가능한 업무부터 에이전트화하라

효율이 가장 빨리 나오는 순서:

1. 테스트/리팩터링
2. 로그 분류/이상 징후 탐지
3. 데이터 정합성 점검
4. 반복 리서치/요약

정답 검증이 가능한 영역에서 먼저 ROI를 만든 뒤, 점차 전략 업무로 확장한다.

### 3) 팀 KPI를 "산출량"이 아니라 "리드타임·재작업률"로 바꿔라

에이전트 도입 효과는 보통 다음에서 먼저 보인다.

- PR 사이클 타임 감소
- 배포 전 버그 재오픈율 감소
- 실험 아이디어→실행까지의 리드타임 감소

즉 "얼마나 많이 만들었나"보다 "얼마나 빨리, 덜 깨지게 만들었나"가 핵심 지표다.

### 4) 개인 경쟁력은 모델 지식보다 "하네스 설계력"에서 갈린다

앞으로 차별화 포인트는 다음 능력이다.

- 문제를 에이전트가 실행 가능한 단위로 분해
- 도구 체인과 검증 루프 설계
- 실패 모드(환각/권한오류/타임아웃) 대비
- 최종 의사결정 지점에서 사람 개입 기준 정의

### 5) 조직 리스크도 같이 설계하라

에이전트 생산성은 강력하지만, 품질 리스크도 함께 커진다.

- 승인 게이트(배포/결제/권한변경)
- 감사로그
- 재현 가능한 실행 기록
- "자동 실행 금지 구간" 명시

성능 경쟁 전에 안전한 운영 모델을 잡아야 지속 가능하다.

## 한 줄 정리

**AI 시대의 승부처는 더 똑똑한 모델을 고르는 일이 아니라, 에이전트가 실제로 일을 끝내도록 만드는 실행 시스템을 설계하는 능력이다.**
