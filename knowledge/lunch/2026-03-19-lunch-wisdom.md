## 🎯 The Big Idea

**AI 제품 개발의 진짜 어려움은 '작동'에서 '신뢰'로의 도약이다.**

데모에서 완벽하게 작동하는 AI 기능이 실제 사용자 손에 가면 왜 망가지는가? 왜 실험실에서 90% 정확도를 자랑하던 모델이 진짜 환경에서는 형편없는 경험을 제공하는가? 

핵심은 이것이다: **AI는 혼돈을 만났을 때 구조를 '발명'한다.** 그리고 그 순간 사용자의 신뢰가 무너진다.

AI 제품 감각(AI Product Sense)이란, 모델이 무엇을 할 수 있고 어디서 실패하는지 이해하고, 그 제약 안에서 사람들이 사랑할 제품을 만드는 능력이다. 이것이 이제 PM의 핵심 역량이 되었다.

## 📊 Argument Breakdown: 단계별 논리 해설

### 1. 현실 인식: Meta의 새로운 면접 방식

**주장:** Meta는 5년 만에 처음으로 PM 면접 프로세스를 변경했다. "Product Sense with AI"라는 새 면접이 추가되었다.

**왜 중요한가:** 
- 후보자는 실시간으로 AI를 사용해 제품 문제를 해결해야 한다
- 평가 기준이 "영리한 프롬프트"나 "화려한 데모"가 아니라, **불확실성과 함께 일하는 능력**이다
- 모델이 언제 추측하는지 알아차리고, 올바른 후속 질문을 하며, 불완전한 정보로도 명확한 제품 결정을 내릴 수 있는가?

**시사점:** 업계 최고 수준 기업이 채용 기준을 바꿨다는 것은, AI 제품 개발의 게임 규칙 자체가 바뀌었다는 신호다.

---

### 2. 핵심 문제: 실험실 vs 현실의 괴리

**사례:** 10년간 음성 인식(speech recognition)과 화자 식별(speaker identification)을 개발한 저자의 경험

> "실험실에서 90% 이상 정확도를 기록한 모델이 실제 집에서 테스트하는 순간 완전히 망가졌다. 개 짖는 소리, 식기세척기 돌아가는 소리, 멀리서 말하는 사람—갑자기 '훌륭한' 모델이 망가진 것처럼 느껴졌다. 그리고 사용자 관점에서, 그것은 정말로 망가진 것이었다."

**교훈:** "작동한다"와 "신뢰할 수 있다" 사이에는 거대한 간극이 있다.

---

### 3. 해결책: 주간 15분 의식(Weekly 15-Minute Ritual)

저자는 실전에서 검증된 **3단계 워크플로우**를 제시한다:

#### **단계 1: 실패 패턴 찾아내기 (Failure Signature 매핑)**

**핵심 인사이트:** 모든 AI 기능은 "실패 서명"이 있다. 세상이 복잡해질 때 어떤 식으로 망가지는지 예측 가능한 패턴이 존재한다.

**실습 방법:** 
1. **혼돈 속 구조화 테스트 (Chaos to Structure Test)**
   - 실제 PM이 매일 다루는 엉망진창 데이터를 모델에 던져라 (Slack 스레드, 회의 노트, Jira 코멘트 등)
   - "전략적 결정 추출해줘"라고 요청
   - **결과:** 모델은 혼돈을 만나면 자신 있게 구조를 **발명한다**

**예시:**
```
Alice: "Stripe failing for EU users again?"
Ben: "no idea, might be webhook?"
Sara: "lol can we not rename the onboarding modal again?"
Kyle: "Still haven't figured out what to do with dark mode"
Alice: "We need onboarding out by Thursday"
Ben: "Wait, is the banner still broken on mobile???"
Sara: "I can fix the copy later"
```

이 스레드를 주고 "Q4 로드맵 작성해줘"라고 하면?

**모델 출력 (나쁜 버전):**
- 명확한 로드맵 생성
- 담당자 할당
- 기한 명시
- **문제:** 전부 거짓이다. 누구도 동의하지 않았고, 결정된 것도 없다.

**개선된 프롬프트:**
> "다시 시도해, 하지만 스레드에서 **명시적으로 언급된 항목만** 포함해. 정보가 부족하면 '정보 부족'이라고 말해."

**모델 출력 (좋은 버전):**
- 명확한 결정 부재 인정
- 핵심 테마만 추출 (발명하지 않음)
- 명시적 할당이 없으면 담당자 지정하지 않음
- 불확실성을 숨기지 않고 드러냄

**AI 제품 감각이 날카로워지는 순간:**
- 무엇이 변했는가?
- 어떤 가드레일이 환각(hallucination)을 고쳤는가?
- 모델이 신뢰성 있게 작동하려면 무엇이 필요한가? (명시적 제약? 더 나은 컨텍스트? 범위 좁히기?)
- "좋은" 버전이 출시 가능하게 느껴지는가, 아니면 여전히 취약한가?

2. **모호성 스트레스 테스트 (Ambiguity Stress Test)**

**핵심 인사이트:** 모호성은 확률적 시스템에게 크립토나이트다. 모델이 사용자의 의도를 완전히 이해하지 못하면, 빈 공간을 추측으로 채운다.

**실습 방법:**
- NotebookLM에 PRD 업로드
- "VP of Product를 위해 요약해줘" 요청
- 결과 관찰:
  - 과도하게 요약했나?
  - 무관한 세부사항에 집착했나?
  - 주의사항을 무시했나?
  - 잘못된 청중을 가정했나?

**예시 테스트 프롬프트:**

| 모호한 프롬프트 | 가능한 해석들 | 테스트 방법 |
|---------------|-------------|-----------|
| "이 Slack 스레드를 요약해줘" | - 리더용? 실행용? 아카이브용?<br>- 무엇을 우선순위로? | 각 의도마다 한 번씩 실행 |
| "이것에 대한 분석 보여줘" | - 트렌드? 성과? 예측?<br>- 어떤 지표? | 명시적으로 지정해서 비교 |
| "PRD 요약해줘" | - 누구를 위한 것?<br>- 어떤 깊이? | 다양한 청중 시뮬레이션 |

**교훈:** 모델이 혼란스러워하는 지점이 정확히 **제품이 개입해야 할 지점**이다.

3. **추론 한계 찾기 (Reasoning Limit Test)**

**목표:** 인간 PM에게는 간단하지만 모델의 추론, 컨텍스트, 판단을 스트레스하는 작업을 선택하라.

**예시 작업들:**

| 작업 | 왜 어려운가 | 무엇을 배우는가 |
|-----|----------|--------------|
| 모순된 피드백 조정 | 여러 관점 균형 | 언제 혼란스러워하는가 |
| 경쟁 우선순위 분류 | 암묵적 트레이드오프 | 어떤 맥락을 놓치는가 |
| 일부 정보로 결정 제안 | 불완전한 입력 처리 | 어디서 추측하기 시작하는가 |
| 정성적 데이터에서 패턴 찾기 | 미묘한 신호 감지 | 무엇을 놓치는가 |
| 큰 컨텍스트 윈도우에서 작업 | 긴 문서, 여러 소스 | 컨텍스트가 커질수록 성능이 어떻게 떨어지는가 |

**핵심:** 모델이 **처음으로 망가지는 지점**이 정확히 **가드레일이 필요한 곳**이다.

---

#### **단계 2: 최소 실행 가능 품질 정의 (MVQ: Minimum Viable Quality)**

**개념:** 전통적 MVP(Minimum Viable Product)와 달리, AI는 MVQ가 필요하다.

**MVQ의 3가지 임계값:**

1. **Acceptable Bar (수용 가능 기준):**
   - 실제 사용자에게 충분히 좋은 수준
   - 예: 일반적인 가정 환경에서 화자를 x% 정확도로 식별

2. **Delight Bar (기쁨 기준):**
   - 기능이 마법처럼 느껴지는 수준
   - 신호: 사용자가 명령을 반복하거나 재구성하지 않음
   - "아니, 내 말은..." 수정이 급격히 감소
   - **경험 법칙:** 10번 시도 중 8-9번 성공하면 마법, 5번 중 1번 재시도 필요하면 신뢰 급속 하락

3. **Do-Not-Ship Bar (절대 출시 불가 기준):**
   - 신뢰를 깨뜨릴 수용 불가능한 실패율
   - 예: 중요한 흐름(구매, 메시지, 개인화)에서 화자를 y% 이상 잘못 식별
   - 사용자가 인식되기 위해 여러 번 반복해야 함

**MVQ 설정을 결정하는 5가지 요소:**

| 요소 | 영향 | 제품 결정 |
|-----|-----|---------|
| **위험도** | 높음 (금융 거래) vs 낮음 (노래 제안) | 고위험 → 더 높은 기준 필요 |
| **비용** | 비싼 모델 호출 vs 저렴한 추론 | 비용이 높으면 기준을 낮춰야 할 수도 |
| **대안** | 대체재 있음 vs 없음 | 대안 없으면 낮은 기준도 가치 있을 수 있음 |
| **채택 단계** | 베타 vs 전면 출시 | 베타는 관대, 출시는 엄격 |
| **전략적 중요도** | 핵심 기능 vs 부가 기능 | 핵심이면 높은 기준, 실험이면 유연 |

**비용 봉투(Cost Envelope) 계산:**

```
예: AI 회의 요약 기능
- 호출당 비용: 30분 전사본 처리에 ~$0.02
- 평균 사용량: 20회의/사용자/월 → ~$0.40/월/사용자
- 헤비 유저: 100회의/월 → ~$2.00/월/사용자
- 캐싱 + 작은 모델 활용 → ~$0.25–$0.30/월/사용자

판단:
✅ $0.30/사용자/월 + 리텐션 증가 = 노브레이너
❌ $5/사용자/월 + 불명확한 임팩트 = 비즈니스 문제
```

**AI 제품 감각의 핵심:** 제안하는 것이 **비즈니스 관점에서 실제로 의미가 있는가?**

---

#### **단계 3: 가드레일 설계 (Design Guardrails)**

**정의:** 가드레일은 모델이 한계에 부딪혔을 때 제품이 무엇을 해야 하는지 결정한다. 사용자가 혼란스럽거나 오도되거나 신뢰를 잃지 않도록 보호한다.

**실제 사례:** Slack 스레드 요약 기능

**문제:**
- 긴 Slack 스레드를 "결정사항과 액션 아이템"으로 요약
- 테스트에서는 잘 작동
- 하지만: 아무도 실제로 동의하지 않았는데도 액션 아이템에 담당자 할당
- 때로는 잘못된 사람 선택

**해결책:**
시스템 프롬프트에 간단한 규칙 하나 추가:

> "누군가 명시적으로 자원하거나 직접 요청받고 확인한 경우에만 담당자를 할당하라. 그렇지 않으면 테마를 드러내고 사용자에게 다음에 무엇을 할지 물어봐라."

**결과:** 이 단일 제약이 가장 큰 신뢰 문제를 거의 즉시 제거했다.

**가드레일의 종류:**

| 실패 패턴 | 제품 갭 유형 | 구체적 수정 방법 |
|---------|------------|---------------|
| 정보 없이 환각 | 맥락 부족 | RAG/검색 추가, 더 나은 프롬프트 |
| 모호한 의도 오해 | 명확성 부족 | 사용자에게 선택/명확화 요청하는 UX |
| 범위 벗어남 | 제약 부족 | 시스템 프롬프트에 명시적 경계 |
| 틀린데도 자신있음 | 신뢰 신호 부족 | 불확실성 UI, 대안 제시 |

## 🌍 Context: 왜 지금 이 글이 중요한가?

### 1. AI 제품 개발의 패러다임 전환

**2024-2025:** "AI를 우리 제품에 추가할 수 있을까?"  
**2026 이후:** "AI 제품이 실제 세계에서 어떻게 작동할까?"

질문 자체가 바뀌었다. 기술적 가능성에서 행동적 신뢰성으로.

### 2. Meta의 시그널

Meta가 5년 만에 PM 면접을 바꿨다는 것은 단순한 채용 정책 변경이 아니다. 이는:
- **업계 표준의 재정의:** 다른 빅테크들도 곧 따라올 것
- **역량의 재구성:** "제품 감각"의 정의 자체가 진화 중
- **실무의 현실:** 이미 내부에서 이런 역량이 필수가 되었다는 증거

### 3. 비용의 경제학

AI 기능의 숨겨진 비용이 점점 더 명확해지고 있다:
- GPT-4 호출 비용
- 컨텍스트 윈도우 증가에 따른 토큰 비용
- 캐싱, 디스틸레이션, 작은 모델 전략의 필요성

**현실:** 많은 스타트업이 마법같은 데모를 만들었다가 비용 때문에 규모 확장을 못하고 있다.

### 4. 신뢰의 위기

AI가 "자신 있게 틀린" 패턴이 너무 자주 반복되면서:
- 사용자 신뢰가 급속히 하락
- 한 번 신뢰를 잃으면 회복이 매우 어려움
- "작동하지만 신뢰할 수 없는" 기능은 사용되지 않는 기능

```markdown
- 개선된 프롬프트:
- 배운 점:

#### 2. Ambiguity Stress Test (5분)
- 테스트한 모호한 요청:
- 모델의 오해:
- 의도 명확화 방법:
- 제품 디자인 아이디어:

#### 3. Reasoning Limit Test (5분)
- 테스트한 복잡한 작업:

- 다음 단계:
```

### 2. 팀 수준 (주간 리뷰)

**금요일 오후 30분 "AI Trust Review":**

1. **이번 주 발견한 실패 패턴 공유**
   - 각자의 15분 의식에서 나온 인사이트
   - 실제 프로덕션에서 발견된 이슈

2. **MVQ 체크인**
   - 현재 기능이 어느 바에 있는가?
   - Acceptable? Delight? Do-not-ship?
   - 비용은 여전히 감당 가능한가?

3. **가드레일 업데이트**
   - 어떤 새로운 제약이 필요한가?
   - 어떤 프롬프트 개선이 효과적이었나?

### 3. 개인 성장 로드맵

**Week 1-4: Foundation**
- 매주 15분 의식 실천
- 3가지 테스트 모두 수행
- 노트 작성

**Week 5-8: Pattern Recognition**
- 반복되는 실패 패턴 인식
- 자주 등장하는 가드레일 종류 파악
- 모델별 특성 이해 (GPT-4 vs Claude vs Gemini)

**Week 9-12: Strategic Thinking**

- 시스템 레벨 통찰 (워크플로우 변화, 기대치 리셋 등)

## 🔥 Key Takeaways

1. **AI 제품 감각은 연습으로 얻는다**
   - 이론이 아니라 루틴이다
   - 주당 15분이면 충분하다
   - 실패를 일찍, 자주 경험하라

2. **모델은 혼돈을 만나면 구조를 발명한다**
   - 이것이 가장 위험한 패턴이다
   - 환각은 자신감 있게 나타난다
   - 가드레일로 보호하라

3. **"작동"과 "신뢰" 사이에는 거대한 간극이 있다**
   - 실험실 정확도 ≠ 실제 신뢰성
   - MVQ로 기준을 명시하라
   - 비용도 신뢰의 일부다

4. **실패 지점이 곧 제품 디자인 지점이다**
   - 모델이 혼란스러워하는 곳 = 제품이 개입해야 할 곳
   - 가드레일은 사후 조치가 아니라 핵심 기능이다
   - 불확실성을 숨기지 말고 드러내라

5. **비즈니스 감각도 제품 감각이다**
   - 마법같은 데모 ≠ 지속 가능한 비즈니스
   - 비용 봉투를 초기에 계산하라
   - 10배 스케일 시나리오를 항상 고려하라
