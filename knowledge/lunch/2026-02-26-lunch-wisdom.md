# Ladybird Adopts Rust, With Help From AI

**Date:** 2026-02-26  
**Source:** [Ladybird Blog](https://ladybird.org/posts/adopting-rust/)  
**Author:** Andreas Kling (Founder & President, Ladybird)

---

## 🎯 The Big Idea

**"AI 코딩 도구는 코드 번역의 게임 체인저다"**

Ladybird 브라우저 프로젝트가 C++에서 Rust로 전환을 결정하면서, 25,000줄의 JavaScript 엔진 코드를 단 2주 만에 포팅했습니다. 사람이 직접 하면 몇 달 걸릴 작업을, Claude Code와 Codex를 사용해서 달성했습니다. 핵심은 **"자율 코드 생성이 아니라, 인간이 주도하는 번역"**이었다는 점입니다.

---

## 📊 Argument Breakdown

### 1. 왜 Rust인가? (The Pragmatic Choice)

Ladybird 팀은 2024년에 Rust를 평가했지만, 당시에는 거부했습니다:
- **문제:** Rust의 ownership 모델이 웹 플랫폼의 1990년대식 OOP 스타일(가비지 컬렉션, 깊은 상속 계층)과 맞지 않았습니다.
- **재평가:** Swift도 시도했지만, C++ interop이 부족하고 Apple 생태계 밖에서는 지원이 제한적이었습니다.
- **결론:** Rust는 성숙한 에코시스템과 안전성 보장을 제공합니다. Firefox와 Chromium도 이미 Rust를 도입했습니다.

**핵심 통찰:** 완벽한 fit이 아니더라도, **실용적 선택(pragmatic choice)**이 때로는 최선입니다.

---

### 2. AI 도구를 활용한 포팅 전략

#### 포팅 대상: LibJS (JavaScript Engine)
- **왜 LibJS?** Lexer, parser, AST, bytecode generator는 상대적으로 독립적이고, test262를 통한 광범위한 테스트 커버리지가 있었습니다.

#### AI 도구 사용 방식
1. **인간 주도 번역 (Human-Directed Translation)**
   - "무엇을" 포팅할지, "어떤 순서로" 할지, Rust 코드가 "어떻게 보여야 할지"는 모두 Andreas가 결정했습니다.
   - Claude Code와 Codex는 "수백 개의 작은 프롬프트"에 응답하며, 원하는 방향으로 코드를 생성했습니다.

2. **Adversarial Review**
   - 초기 번역 후, 여러 모델에게 "실수와 나쁜 패턴을 찾아라"는 적대적 리뷰를 수행했습니다.

3. **Byte-for-Byte 검증**
   - C++ 파이프라인과 Rust 파이프라인이 **동일한 AST**와 **동일한 bytecode**를 생성하는지 검증했습니다.

**결과:**
- 25,000줄의 Rust 코드
- 포팅 기간: 2주 (사람이 직접 하면 몇 달)
- test262: 52,898개 테스트, **0개 리그레션**
- Ladybird regression tests: 12,461개 테스트, **0개 리그레션**
- **성능 리그레션도 0**

---

### 3. "Translated from C++" 스타일의 의도적 선택

생성된 Rust 코드는 idiomatic Rust가 아닙니다:
- **의도적 선택:** C++ 파이프라인과의 호환성이 최우선입니다.
- **예시:** C++의 register allocation 패턴을 Rust에서도 그대로 모방해서, 두 컴파일러가 동일한 bytecode를 생성하도록 했습니다.
- **미래 계획:** C++ 파이프라인을 폐기한 후, idiomatic Rust로 리팩토링할 계획입니다.

**핵심 통찰:** 코드 품질보다 **정확성(correctness)**과 **호환성(compatibility)**이 먼저입니다.

---

### 4. 앞으로의 방향

- **점진적 전환:** Rust 포팅은 "부업(sidetrack)"으로 진행되며, 메인 프로젝트는 계속 C++로 개발됩니다.
- **선택적 포팅:** 어떤 부분을 언제 포팅할지는 코어 팀이 관리합니다.
- **Interop 경계:** 새 Rust 코드는 기존 C++ 코드와 명확한 경계를 통해 공존합니다.

## 🌍 Context: Why This Matters Now

### 1. 브라우저 엔진의 메모리 안전성 문제
- **역사:** 브라우저는 인터넷의 관문이지만, C++의 메모리 안전성 이슈는 끊임없는 보안 취약점의 원인입니다.
- **현재:** Firefox와 Chromium이 이미 Rust를 도입하고 있으며, Ladybird도 이 흐름에 합류했습니다.

### 2. AI 코딩 도구의 성숙
- **2024년의 평가:** Rust를 거부했습니다.
- **2026년의 현실:** Claude Code와 Codex 같은 AI 도구가 성숙해지면서, 대규모 코드 마이그레이션이 현실적으로 가능해졌습니다.
- **시사점:** AI 도구는 단순히 "코드 생성기"가 아니라, **대규모 번역/마이그레이션 프로젝트의 가속기**입니다.

### 3. "인간 주도 + AI 보조" 패턴의 증거
- **자율 코드 생성 vs. 인간 주도 번역:** Ladybird의 성공은 "인간이 전략을 세우고, AI가 실행한다" 패턴이 효과적임을 증명합니다.
- **Adversarial Review:** AI를 AI로 검증하는 다층 검증 패턴도 흥미롭습니다.

## 💻 Application: What Developers Can Learn

### 1. 레거시 코드 마이그레이션의 새로운 가능성
**상황:**
- 당신의 팀은 10만 줄짜리 Python 2 코드베이스를 Python 3로 옮기고 싶지만, 리소스가 부족합니다.

**적용:**
1. **작은 모듈부터 시작:** LibJS처럼 독립적이고 테스트 커버리지가 좋은 부분을 선택하세요.
2. **인간 주도 번역:** Claude Code에게 "이 모듈을 Python 3로 번역해줘"가 아니라, "이 함수의 print 문을 Python 3 스타일로 바꿔줘" 같은 작은 프롬프트를 수백 번 날리세요.
3. **Byte-for-Byte 검증:** 입력/출력을 비교하는 자동화된 테스트를 작성하세요.
4. **Adversarial Review:** 다른 모델(GPT, Gemini 등)에게 "이 코드에서 실수를 찾아봐"라고 요청하세요.

---

### 2. "Pragmatic Choice" vs. "Perfect Fit"
**교훈:**
- Rust는 Ladybird의 OOP 스타일에 완벽하게 맞지 않았습니다. 하지만 **성숙한 에코시스템**과 **안전성 보장**이 더 중요했습니다.
- Swift는 기술적으로 더 나았을 수 있지만, **플랫폼 지원**이 부족했습니다.

**적용:**
- 기술 선택 시, "완벽한 fit"을 찾기보다는 **장기적 지속 가능성**, **커뮤니티 지원**, **에코시스템 성숙도**를 우선하세요.
- "일단 시작하고, 나중에 리팩토링"하는 접근도 유효합니다.

---

### 3. AI 코딩 도구 활용 전략
**나쁜 사용:**
- "Claude, 이 전체 프로젝트를 Rust로 바꿔줘" (자율 코드 생성)

**좋은 사용:**
1. **작은 단위로 쪼개기:** 함수 하나, 클래스 하나씩 번역하세요.
2. **명확한 목표 설정:** "이 함수의 동작을 유지하면서 Rust의 ownership 모델을 사용하도록 바꿔줘"
3. **다층 검증:** 초기 번역 → Adversarial Review → 사람의 최종 검토
4. **자동화된 회귀 테스트:** 원본과 번역본이 동일한 결과를 내는지 지속적으로 검증하세요.

---

### 4. "Idiomatic" vs. "Compatible"
**Ladybird의 선택:**
- 첫 번째 목표는 "idiomatic Rust"가 아니라 **"C++와 호환되는 Rust"**였습니다.
- 나중에 C++ 파이프라인을 폐기한 후, idiomatic Rust로 리팩토링할 계획입니다.

**적용:**
- 대규모 마이그레이션 시, **정확성(correctness)**과 **호환성(compatibility)**을 먼저 확보하세요.
- "완벽한 코드"는 나중에 작성해도 됩니다. 먼저 **동작하는 코드**를 만드세요.

---

### 5. 점진적 전환의 중요성
**Ladybird의 전략:**
- Rust 포팅은 "부업"으로 진행되며, 메인 프로젝트는 계속 C++로 개발됩니다.
- 새 Rust 코드는 기존 C++ 코드와 명확한 경계를 통해 공존합니다.

**적용:**
- 레거시 시스템을 마이그레이션할 때, **"빅뱅 전환"보다는 "점진적 전환"**이 안전합니다.
- 새 기술과 기존 기술이 공존할 수 있는 **interop 경계**를 설계하세요.

---

## 🔥 Key Takeaways

1. **AI 도구는 대규모 코드 마이그레이션을 가속화한다:**  
   25,000줄을 2주 만에 포팅 (사람이 직접 하면 몇 달).

2. **인간 주도 번역 > 자율 코드 생성:**  
   "무엇을", "어떻게", "언제" 할지는 인간이 결정하고, AI는 실행한다.

3. **Adversarial Review로 품질 검증:**  
   여러 모델을 동원해서 "실수 찾기"를 시킵니다.

4. **Pragmatic Choice > Perfect Fit:**  
   완벽한 fit이 아니더라도, 성숙한 에코시스템과 안전성 보장이 더 중요할 수 있습니다.

5. **정확성 먼저, 품질은 나중에:**  
   첫 번째 목표는 "동작하는 코드"입니다. Idiomatic 코드는 나중에 작성해도 됩니다.

6. **점진적 전환 전략:**  
   Rust와 C++가 공존하는 interop 경계를 설계하고, 선택적으로 포팅합니다.

---

## 💡 Final Thought

**"AI 코딩 도구는 번역기가 아니라, 협업 파트너다"**

Ladybird의 사례는 AI 도구가 단순히 코드를 생성하는 것이 아니라, **인간의 전략적 판단을 증폭시키는 도구**임을 보여줍니다. 핵심은 "AI에게 모든 것을 맡기는 것"이 아니라, **"AI를 어떻게 지휘할 것인가"**입니다.

당신의 레거시 코드베이스도 마찬가지입니다. 작은 모듈부터 시작하고, 명확한 목표를 설정하고, 다층 검증을 거치면, 당신도 Ladybird처럼 몇 달 걸릴 일을 몇 주 만에 끝낼 수 있습니다.

**행동 지침:**
1. 이번 주에 마이그레이션하고 싶은 작은 모듈 하나를 선택하세요.
2. Claude Code나 Codex에게 작은 프롬프트를 수십 번 날려서 번역하세요.
3. 자동화된 회귀 테스트를 작성하고, 원본과 번역본의 동작을 비교하세요.
4. 다른 AI 모델에게 "실수 찾기"를 시키세요.
5. 결과를 팀과 공유하세요.

**"일단 시작하세요. 완벽은 나중에 옵니다."**
