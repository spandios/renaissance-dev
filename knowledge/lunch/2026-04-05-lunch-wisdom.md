# 점심 지식 Deep Dive: 컨텍스트는 채팅에 두지 말고, 문서에 고정하라

**Source:** [Context Anchoring](https://martinfowler.com/articles/reduce-friction-ai/context-anchoring.html)  
**Author:** Martin Fowler  
**Date:** 2026-04-05

---

## The Big Idea

**AI와 협업하는 개발에서 가장 큰 생산성 손실은 모델 성능이 아니라 ‘결정의 이유(why)가 채팅 히스토리에 갇혀 사라지는 것’이며, 이를 막는 핵심 방법은 기능 단위의 살아있는 문서(Feature Doc)로 컨텍스트를 고정(anchoring)하는 것이다.**

---

## Argument Breakdown

### 1) 문제는 “기억 부족”이 아니라 “기억 위치”다

긴 AI 세션에서 우리는 보통 이렇게 행동한다.
- 세션을 닫으면 맥락이 날아갈까 불안해서 계속 붙잡음
- 대화가 길어질수록 품질이 떨어져도 끊지 못함

글은 이를 정확히 찌른다. **문제는 AI가 멍청해서가 아니라, 중요한 맥락이 채팅이라는 휘발성 매체에만 존재한다는 점**이다.

### 2) 왜 긴 대화에서 품질이 무너지는가

컨텍스트 윈도우가 커졌어도 한계는 여전히 존재한다. 게다가 중요한 건 단순 용량이 아니라 **위치 효과**다.

- 앞/뒤 토큰은 상대적으로 잘 반영
- 중간에 묻힌 정보는 더 잘 잊힘
- 특히 “무엇을 선택했는지”보다 “왜 그렇게 선택했는지”가 먼저 흐려짐

그래서 AI가 표면적으로는 맞는 선택(예: PostgreSQL 사용)을 하면서도, 의도와 충돌하는 제안(설계 철학 위반)을 하게 된다.

### 3) 자동 요약/압축은 만능이 아니다

도구가 대화 히스토리를 자동 압축해도, 개발자는 보통 아래를 통제할 수 없다.
- 무엇이 원문으로 보존됐는지
- 무엇이 요약됐는지
- 무엇이 버려졌는지

이때 가장 취약한 건 역시 **설계 근거와 트레이드오프**다. 즉, 코드보다 설명이 먼저 사라진다.

### 4) 해결책: Feature-level External Memory

글의 제안은 간단하고 강력하다.

- 프로젝트 전반 규칙은 **Priming Doc**(상대적으로 안정적)
- 기능별 결정 이력은 **Feature Doc**(세션마다 업데이트)

Feature Doc에는 보통 아래가 들어간다.
- 결정 사항(무엇을 선택)
- 선택 이유(왜 선택)
- 거절한 대안(무엇을 버림)
- 남은 질문(Open Questions)
- 현재 진행 상태(State)

핵심은 코드가 아닌 **의사결정 기록**을 남기는 것이다.

### 5) 이건 사실 “실시간 ADR”이다

Fowler는 이를 ADR 철학과 연결한다.

- 코드는 결과(outcome)를 보여주지만
- ADR/Feature Doc은 판단 과정(reasoning)을 남긴다

즉 Feature Doc은 “나중에 쓰는 문서”가 아니라, **지금 의사결정이 만들어지는 순간에 쓰는 살아있는 ADR**이다.

## Context: 왜 지금 중요한가

2026년 개발팀은 에이전트를 점점 오래, 자주 사용한다. 이때 생산성을 깎아먹는 병목은 대체로 아래다.

1. 세션 간 재온보딩 비용 (매번 다시 설명)
2. 팀원/에이전트마다 다른 맥락으로 인한 중복 논쟁
3. 설계 근거 소실로 인한 “맞는 코드지만 틀린 방향” 증가

결국 성능 좋은 모델을 쓰는 것만으로는 해결되지 않는다. **컨텍스트를 지속 가능하게 관리하는 운영 습관**이 팀 성능을 가른다.

## Application: 개발자로서 어떻게 적용할 것인가

### 1) 세션 종료 기준을 바꾼다

다음 질문에 “예”면 세션 종료:
> 지금 세션을 닫고 새로 시작해도 불안하지 않은가?

불안하다면 이유는 대개 하나다. 결정 근거가 문서에 없다.

### 2) beauty-sale에 바로 적용할 Feature Doc 템플릿

기능 단위로 아래 5블록만 유지:
1. **Decisions** (선택 + 이유 + 대안)
2. **Constraints** (멀티테넌시, 이벤트 스키마, SLA 등)
3. **Open Questions** (PM/디자인 확인 필요 항목)
4. **State** (완료/다음 작업)
5. **Metrics Link** (PostHog 이벤트/대시보드 링크)

특히 현재처럼 `view_item` 누락 같은 계측 이슈는 “수정 코드”보다 “왜 스키마를 이렇게 유지하는지”가 먼저 기록돼야 재발을 줄일 수 있다.

### 3) 팀 협업 규칙으로 승격

- PR 리뷰 전, 관련 Feature Doc 최신화가 선행 조건
- 세션 시작 시 Priming Doc + Feature Doc 함께 주입
- 주 1회 Open Questions 정리 후 ADR로 승격

이렇게 하면 “사람-에이전트-사람” 핸드오프 비용이 눈에 띄게 줄어든다.

### 4) 면접/이직 연결 포인트

시니어 인터뷰에서 강한 답변은 “AI를 쓸 줄 안다”가 아니다.

- **세션 의존성을 줄이는 운영 방식**
- **설계 근거를 재사용 가능한 형태로 축적한 경험**
- **개발 속도와 품질을 함께 유지한 프로세스 설계**

이 3가지를 사례로 말할 수 있으면, 프로덕트 엔지니어 포지션에서 확실히 차별화된다.

## 한 줄 정리

**AI 시대의 생산성은 프롬프트 품질보다, ‘결정을 사라지지 않게 저장하는 시스템’을 갖췄는지에서 갈린다.**
